# Explain the ledger in 90 seconds

Draw two tables. In `events(seq PRIMARY KEY, delta)`, a row records the first durable payload for that sequence. The single `checkpoint(cursor, balance)` row answers a different question: how far can the consumer apply the stream without skipping anything? SQLite stores the balance as decimal text so a sum of signed 64-bit deltas can grow beyond 64 bits.

1. Deliver `1:+5`. Write the event and checkpoint `(1,5)` in one transaction. Deliver `3:+2`. Save the row, but leave the checkpoint at `(1,5)` because sequence 2 is missing.
2. Deliver `2:-1`. The transaction inserts 2 and sees both 2 and 3 in order. The checkpoint becomes `(3,6)`. An identical payload for 3 is now a duplicate. A new delta for 3 conflicts with the retained row.
3. Draw a line at COMMIT. Kill the worker on either side. Before the line, the transaction rolls back and the retry returns `accepted`. After the line, the sender still gets no receipt, but the retry returns `duplicate`. The rows and the checkpoint agree in both cases.
4. Move the insert into a separate commit. A kill immediately after that commit leaves all three rows durable and the checkpoint at `(1,5)`. Retrying 2 sees its stored identity and returns a duplicate with the stale checkpoint. The complete durable prefix already sums to 6. This is why checking the receipt or row count alone misses the failure.

Run `test/whiteboard` from the project root to compare the deliberately broken scratch copy with the intact executable. Run `bin/demo` for the two supported crash seams.

## How the design translates to production

**PostgreSQL.** Give each stream a checkpoint row and use a unique key on `(stream_id, seq)` for events. In one transaction at READ COMMITTED, lock the stream checkpoint with `SELECT ... FOR UPDATE` before reading or inserting its event. All writers for that stream must take that lock first. Compare any existing delta, drain the prefix, and commit the checkpoint before returning a receipt. Two workers racing on one stream then serialize, while independent streams can advance concurrently. On a deadlock or serialization failure, retry the entire transaction with a bounded deadline. [PostgreSQL row locks](https://www.postgresql.org/docs/current/explicit-locking.html) · [Transaction retries](https://www.postgresql.org/docs/current/mvcc-serialization-failure-handling.html)

**Kafka or SQS.** Commit the SQLite event and checkpoint before acknowledging delivery. For Kafka, disable automatic offset commits and commit the next offset only after all earlier offsets in the partition have durable outcomes. For SQS, delete the message after that commit. A death in between can redeliver the message. A stable application sequence and its original delta absorb the replay. If processing also sends an email or charges a card, store an outbox entry in the same transaction and use a stable idempotency key with the external service. [Kafka delivery semantics](https://kafka.apache.org/41/design/design/) · [SQS at-least-once delivery](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)

**SQLite durability.** The local benchmark observed DELETE journaling, FULL synchronous mode (2), and 4,096-byte pages. The kill harness terminates a real child while the OS and filesystem stay running. A separate connection checks committed rows before the retry. A host power loss also tests whether the filesystem and device honor flushes. WAL would place committed changes in a separate log until checkpointed into the main file; an open reader can delay checkpoint progress. Include those sidecars in storage accounting and use SQLite-aware backups. The measured journal and synchronous settings are in the [benchmark artifact](../benchmark/results.json). [SQLite synchronization levels](https://sqlite.org/pragma.html#pragma_synchronous) · [Write-ahead logging](https://sqlite.org/wal.html)

## Operating the Shopify ledger

**Poison deliveries.** Backoff alone keeps retrying an order that can never succeed, such as a deleted order or an app whose scope was revoked. After `max_attempts` failures the worker parks the delivery. Parked rows never become eligible again, so they cannot take worker time from healthy orders. `bin/shopify-status` turns a parked row into an alert (exit 2). `bin/shopify-deliveries retry` is the only way back, and it refuses rows that are already processed. Recovery after the cause is fixed is idempotent: transaction identity means a retry can never double-count.

**Resumable reconciliation.** A seven-day first scan can be thousands of pages. Restarting from page one after every outage wastes API budget and can starve on a flaky connection. Each page is applied, and then its next cursor is committed to `reconciliation_runs`. Resuming from that cursor is safe only because the window's upper bound is frozen. Orders do not get older: an order updated after the failure now has `updated_at` past the window and is picked up by the next window, which overlaps this one by five minutes. The cursor itself is treated as perishable. If its first reuse fails, it is discarded and the window restarts. That costs extra API calls but no correctness, because pages are idempotent.

**Retry layers.** There are three layers, each bounded. An Admin request retries throttling and 5xx errors within about one second, honouring `Retry-After`. A delivery attempt backs off from 2 to 60 seconds. A delivery parks after `max_attempts`. Malformed data skips the first layer because repeating a bad answer does not fix it. Every query is read-only, so request retries cannot cause side effects in Shopify. The client also reads the GraphQL cost bucket in `extensions.cost` (requested cost, currently available, restore rate). It sizes the throttle wait to the bucket deficit instead of guessing. It also pauses after a success that leaves the bucket too low. With several workers sharing one shop's bucket, pacing is cheaper than hitting the limit and retrying.

**Migrations.** Each version is a list of DDL statements. The expected catalog of each version is computed in memory, and the database's `sqlite_master` is matched against that list. Only later steps run, inside one `BEGIN IMMEDIATE`. SQLite DDL is transactional, so a crash or failed statement leaves the previous version, and two processes opening an old file serialize on the write lock. The second one re-reads the catalog and finds nothing to do. On PostgreSQL, the same idea is a `schema_migrations` table plus an advisory lock. Column additions must stay nullable or defaulted so that old rows remain valid (pre-upgrade transactions report provenance `unknown`).

**Concurrent workers.** The first multi-worker measurement worked correctly, but wasted calls: with 200 deliveries, 2 workers made 314 Admin fetches and 8 made 614. The fix is a claim, `claimed_by` = PID with `claimed_until` = now plus the longest possible fetch, taken in the same `BEGIN IMMEDIATE` that selects the row. A plain lease would break crash recovery, because a worker killed mid-fetch would hide its delivery until the lease expired. Since SQLite is a local file, every worker shares this host's process table. `kill(pid, 0)` tells a dead claimant from a live one, so an orphaned claim is taken over at once. Correctness never depends on the claim. The apply transaction still re-checks `processed = 0`, and payments are keyed by transaction ID. The claim only saves API budget. On PostgreSQL, `SELECT ... FOR UPDATE SKIP LOCKED` inside a short transaction and a `claimed_until` column replace the PID check, because workers would run on other hosts. Shard reconciliation by shop; runs are already limited to one open run per shop.

**Ingest backpressure.** The webhook waits only 250 ms for the SQLite write lock and then answers 503, because Shopify retries non-2xx responses. A retry is safe because `(shop, webhook_id)` deduplicates it. With 8 concurrent senders, about 1.5% of attempts got 503. Nothing was lost or duplicated, and the slowest acknowledgment stayed well under Shopify's 5 s timeout. The worker waits up to 5 s instead, because nobody is waiting on it. The next step for higher ingest is WAL, or a queue in front of the database. Holding the HTTP response longer is not, because Shopify removes webhook subscriptions that keep failing.

**Fleet operations.** `bin/reconcile --all` runs shop by shop and records each failure separately. One merchant's revoked token or outage cannot stall reconciliation for the rest, and the failed run stays resumable. `bin/shopify-status --prometheus` exports counts and ages but deliberately leaves out money: metric samples are floats, and totals must stay exact strings.

**Backups.** Copying the file with `cp` while a worker commits can capture half a transaction. `bin/shopify-backup` uses SQLite's online backup API in a single step, so the copy is one committed snapshot. Because a delivery's payments and its inbox completion commit together, every snapshot has exactly as many payment rows as processed deliveries: copies taken mid-drain held 0, 11, 43, 73 and 105. The copy must pass `integrity_check` and the schema check before it is renamed into place. On PostgreSQL, the equivalent is `pg_dump` (one repeatable-read snapshot) or WAL archiving for point-in-time recovery.

**Deploys and maintenance.** `bin/shopify-worker --watch` only checks for SIGTERM between deliveries, so a deploy cannot interrupt a commit. Even a SIGKILL is safe, because the claim of a dead PID is taken over and the transaction identity makes the replay idempotent. `bin/shopify-maintain` takes SQLite's exclusive lock and fails fast instead of waiting behind writers. A VACUUM that queued behind traffic would turn every webhook into a 503 for the whole rebuild.

**Coalescing.** The worker treats a webhook as a notification to fetch, not as the order's state. Every delivery for the order that committed before the fetch began is answered by that fetch. The fence is the largest inbox `id` for the order, read before the request, so those deliveries are completed in the same transaction as the payments. A delivery that arrives during the fetch has a larger `id`, stays pending and gets its own fetch. That keeps the rule that a fetch must postdate the webhook it answers. The test injects a webhook in the middle of a fetch and expects exactly two fetches for four deliveries.

**Randomized crash testing.** *What:* `bin/shopify-fuzz` generates random operation sequences and checks four invariants after every step. It also checks exact equality with a reference model after a settle phase. *Why:* the example tests each cover one interleaving that I thought of. The fuzzer combines crashes, faults, duplicates, missed webhooks and failing reconciliation pages in orders I did not think of. *Tradeoffs:*
- Most operations run in process for speed. A crash is an exception raised from the worker's commit hooks, so the transaction rolls back (before commit) or stays committed (after commit). The in-process "time advance" sets `next_attempt_at = 0` instead of waiting.
- The real SIGKILL and multi-process paths are behind `--processes`, because each one spawns Ruby.
- The oracle is checked by a planted wrong amount, which must be caught and shrunk.

*At Shopify scale:* the model already runs against a real PostgreSQL (`--postgres`). The next step would be a deterministic simulation of many pods. The faults injected would include network partitions between the worker and the database, not only API faults.

**Payment statuses and currencies.** *What:* every Shopify transaction is kept in `payment_events` with its latest status, and only `SUCCESS` sales, captures and refunds reach the money table. *Why:* a pending capture must not count, but the operator still needs to see it. An authorization must be visible to tell whether captures exceed it. *Tradeoffs:*
- Status only moves from an open status to a final one. A stale fetch that shows an older open status is ignored rather than rejected, because two workers can fetch the same order at different moments.
- Refunds above the collected amount, and captures above their authorization, are reported, not rejected. Shopify is the source of truth, and rejecting would park the delivery forever.
- Presentment money is stored but never converted. Converting would need an exchange rate that the ledger does not own.

**PostgreSQL workers.** *What:* `bin/shopify-pg-worker` claims deliveries with `FOR UPDATE SKIP LOCKED` and a 60 s lease, then applies the shared payment rules through a small adapter. *Why:* SQLite claims rely on PID liveness, which only works on one host. SKIP LOCKED lets many machines pick different rows without waiting on each other. *Tradeoffs:*
- A dead worker's delivery waits up to the lease length before another worker takes it.
- Applying payments is idempotent, so a worker whose lease expired mid-fetch can at worst repeat a fetch. It cannot double-count.
- Ingest (`SHOPIFY_LEDGER_INBOX=postgres`), the worker and reconciliation (through `Postgres::Store`) are ported. The operator tools still read SQLite.

**Moving a shop between databases.** *What:* `bin/shopify-move-shop` copies and verifies, then switches the route, then cleans up. Each step is idempotent, and a crash test covers each seam. *Why:* sharding by shop means a shop eventually has to move without losing or double-counting money. *Tradeoffs:*
- The route lives in the config file, so running processes must be restarted, and ingest must pause during the move.
- With a central routing table and a per-shop write fence, the move could run online.
- Cleanup refuses rather than merging when the old copy changed. Merging two inboxes automatically is exactly where silent loss would hide.

**What the fuzzer found (a story to tell).** When shop moves were added to the fuzzer's operations, the second campaign failed within seconds. The shrinker cut it down to a move that crashed after copying, followed by ordinary work on the old route, then a settle.
- **First bug:** cleanup compared the orphan copy with the routed copy for exact equality, so a copy that had gone stale was refused forever. The fix asks a different question: does the old database hold any delivery or payment that the routed copy lacks? A stale copy loses nothing; an unknown delivery needs an operator.
- **Second bug:** a worker draining the old database kept processing the stale copy's deliveries. Claims now skip shops routed elsewhere.

Each bug got a focused regression test before the fix. *Lesson:* the example tests covered each crash seam on its own. The bugs needed a crash followed by more normal traffic, which is exactly the combination a random sequence produces and a hand-written test does not.

**A bug that SQLite hid.** On SQLite, `BEGIN IMMEDIATE` lets only one writer run at a time, so applying an order's payments never raced. On PostgreSQL at READ COMMITTED, two workers completing different deliveries of the same order both inserted the same transaction row, and the second got `PG::UniqueViolation`. The fix keeps the code portable: insert with `ON CONFLICT DO NOTHING RETURNING 1`, and when nothing was inserted, compare against the row that won. Conflicting facts still raise. *Lesson:* porting to a database with more concurrency moves the serialization point. The regression test holds one transaction open with a second connection blocked behind it, so the race happens every run instead of one run in a thousand.

**A deadlock the fuzzer found.** After the fuzzer started running two PostgreSQL workers at once, one seed hung. Each completion locked its own inbox row and then coalesced the other rows of the same order, so two workers could each hold one row and wait for the other's. The fix is classic lock ordering: lock every same-order row up to the fence in ID order (`ORDER BY id FOR UPDATE`) before applying, so the second completion waits and then sees its row already processed. A four-thread regression test hit `PG::TRDeadlockDetected` in 3 of 3 runs before the fix.

**Porting means porting the guards too.** The SQLite worker only records a failure when `attempts` still matches what it claimed, so a failure that started before an operator retry cannot park the retried delivery. The first PostgreSQL worker dropped that predicate. A review that compared the two workers' `UPDATE` statements line by line found it, and the SQLite race test, rewritten for PostgreSQL, failed with `parked` until the guard came back. Since then, every PostgreSQL write path has been checked against its SQLite twin.

## Notes from the real-store run

- Shopify signs webhooks registered through the Admin API with the app's client secret, so that secret, not the Admin access token, is the HMAC key in the ledger config.
- Against a live development store, `bin/reconcile` matched Shopify's totals to the cent, and a second run changed nothing.
- Shopify's manual test gateway accepts only one capture per authorization, so multiple partial captures are tested against the fake Admin API and in the fuzzer instead.
